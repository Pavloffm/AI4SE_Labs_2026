# Repository-aware source code generation: proposed pipeline

The assignment pipeline splits files into overlapping 80-line chunks, retrieves five with lexical hashed embeddings, and gives them to an LLM alongside the full target file. It completed the ten missing-method tasks and passed 481 tests. That demonstrates this small example works, but does not establish that fixed-size chunks, embedding-only ranking, or five retrieved chunks are generally optimal.

An unconstrained pipeline would work as follows:

1. **Index the repository.** Parse source and tests to build a repository-wide graph of files, classes, methods, imports, references, calls, and test-to-code links. Record paths, signatures, docstrings, return annotations, and source locations. Keep the graph current as files change. This gives a broad map before exploring the local neighborhood of a particular task.
2. **Find candidates using complementary signals.** Search exact names, paths, identifiers, and task terms *and* retrieve semantically similar code with embeddings. Combine and rerank those results using the task's named target, graph proximity, and relevant tests. Embeddings help with descriptions that do not share identifier names; exact search and graph links preserve important relationships that similarity scores can miss. Embedding matching is therefore useful, but not the best strategy on its own.
3. **Retrieve at the right granularity.** Index classes, methods, and tests as separate structural units rather than cutting blindly every 80 lines. Initially show compact representations—names, signatures, return annotations, docstrings, and locations—where available. Fetch full implementations, surrounding class state, callers, or test bodies only when the task needs those details. A summary is a starting point, not a substitute for behavior hidden in an implementation.
4. **Assemble a budgeted prompt.** Always include the request, target method and signature, necessary local context, and the most relevant constraints from tests. Add reranked context until a token budget chosen for the particular model is reached, leaving room for generation and revision. Deduplicate overlapping material and prefer source code over lower-confidence summaries when behavior matters. The number of chunks should vary by task and model, not be fixed at five.
5. **Generate, verify, and revise.** Ask for a minimal patch rather than an unconstrained rewrite. Check that it parses and changes only the intended code; run focused tests, then the wider test suite. If a check fails, provide the failure and relevant source to the model for a bounded revision, and rerun the checks. Report remaining failures rather than claiming success without verification.

This approach trades extra indexing and retrieval work for more precise context. For a tiny repository, a simple exact search and direct source inspection may be cheaper than maintaining a graph or vector database; the hybrid pipeline becomes more valuable as the repository and tasks grow. Compare variants on held-out tasks using retrieval of relevant code, test pass rate, tokens sent, and cost—not just a single successful run.
